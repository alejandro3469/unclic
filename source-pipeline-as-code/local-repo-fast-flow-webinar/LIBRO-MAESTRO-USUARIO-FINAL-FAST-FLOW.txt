2) VISION GENERAL: POR QUE FAST FLOW ENTERPRISE
====================================================================

2.1 El problema que aparece en casi todos los equipos

Muchas organizaciones logran construir features.
Pocas logran entregarlas a ritmo confiable durante meses sin desgaste.

Sintomas comunes:
- releases grandes y espaciados,
- aprobaciones ambiguas,
- diferencias entre ambiente dev, qa y prod,
- rollback lento,
- incidentes repetitivos,
- dependencia de pocas personas.

2.2 Que pasa cuando no se atiende delivery

Consecuencia 1: negocio lento
El valor llega tarde al usuario final.

Consecuencia 2: riesgo alto
Cada despliegue se siente como apuesta.

Consecuencia 3: desgaste humano
El equipo trabaja en modo reaccion.

Consecuencia 4: escalabilidad limitada
A mayor crecimiento, mayor friccion.

2.3 Que propone Fast Flow Enterprise

No propone "mas herramientas" como fin.
Propone una forma de operar:
- flujo estandar,
- evidencia automatizada,
- versionado claro,
- despliegue controlado,
- observabilidad,
- mejora continua.

2.4 Resultado esperado

Velocidad con control.
Confiabilidad sin frenar innovacion.
Autonomia sin dependencia excesiva de terceros.

3) CONCEPTOS BASE EXPLICADOS PARA CUALQUIER PERSONA
====================================================================

3.1 Que es CI/CD

CI (integracion continua): validar cambios de forma frecuente.
CD (entrega/despliegue continuo): llevar cambios validados a ambientes de forma controlada.

En simple:
CI/CD es convertir "pasos manuales inciertos" en "pasos claros y repetibles".

3.2 Que es un pipeline

Un pipeline es una secuencia de etapas.
Ejemplo:
Commit -> Build -> Test -> Lint -> Package -> Push -> Deploy -> Health Check

Cada etapa responde una pregunta:
- Build: compila?
- Test: funciona como esperamos?
- Lint: cumple reglas de calidad?
- Security Scan: hay riesgos criticos?
- Deploy: se puede publicar con control?
- Health Check: quedo saludable?

3.3 Que es una imagen

Una imagen es un paquete ejecutable de aplicacion.
Incluye runtime, dependencias y app.

3.4 Que es un contenedor

Un contenedor es una instancia corriendo de una imagen.
Si la imagen esta bien definida, el comportamiento es mas predecible.

3.5 Que es un registry

Registry = biblioteca central de imagenes versionadas.

Beneficios:
- trazabilidad,
- promocion por entornos,
- rollback rapido,
- control de acceso.

3.6 Que es Kubernetes

Kubernetes administra contenedores para mantener estado deseado.

Beneficios:
- auto-recuperacion,
- escalado,
- despliegues declarativos,
- estabilidad operativa.

3.7 Que es Helm

Helm es una forma de empaquetar y parametrizar despliegues en Kubernetes.

Beneficio central:
Mismo chart, distintos valores por entorno.

3.8 Que es Terraform

Terraform es infraestructura como codigo.
Declara recursos en archivos versionables.

Beneficio central:
Reproducibilidad de entorno y menos configuraciones manuales difusas.

4) PIPELINE AS CODE CON JENKINS (DETALLE OPERATIVO)
====================================================================

4.1 Por que Jenkins sigue siendo relevante

Porque permite:
- definir flujo como codigo,
- integrar pruebas y calidad,
- controlar promociones,
- operar en servidor propio Linux,
- acoplarse a procesos existentes.

4.2 Caso real: pos-online (flujo por ramas)

En pos-online existe un Jenkinsfile que separa comportamiento por rama.

Ramas no-main:
Prepare -> Build -> Test -> Lint

main:
Incluye Package y pasos de Cleanup/Deploy con aprobacion manual.

Esto crea un equilibrio:
- velocidad en desarrollo,
- control adicional en despliegues sensibles.

Snippet real (resumen)
Fuente: /Users/wallfacer/proyectos-gitlab/pos-online/Jenkinsfile

```groovy
stage('Test') {
    steps {
        unstash 'build-output'
        script {
            def test = load '.jenkins/build/test.groovy'
            test.run(this)
        }
        junit allowEmptyResults: true, testResults: 'target/surefire-reports/*.xml'
    }
}

stage('Lint') {
    steps {
        sh 'mvn checkstyle:check -q -DskipTests -Dcheckstyle.failOnViolation=false -Dmaven.repo.local=${MAVEN_REPO_LOCAL} ${MAVEN_CLI_OPTS}'
    }
}
```

Que debe entender un usuario final de este snippet

- "junit" significa que resultados de pruebas se registran y pueden auditarse.
- "checkstyle" significa que hay control de calidad estatico.
- El flujo no depende de memoria humana para recordar validaciones.

4.3 Aprobaciones manuales bien usadas

Aprobacion manual no es anti-automatizacion.
Es una compuerta de riesgo.

Se recomienda en:
- cambios de produccion,
- ventanas sensibles,
- migraciones criticas.

No se recomienda para:
- tareas repetitivas de bajo riesgo que ya estan bien cubiertas por controles.

4.4 Reproducir pipeline localmente

Pos-online incluye script local:
/Users/wallfacer/proyectos-gitlab/pos-online/run-jenkins-pipeline-local.sh

Esto ayuda a:
- detectar fallas antes de llegar a Jenkins,
- reducir ciclos de espera,
- mejorar experiencia de desarrollo.

Snippet real

```bash
mvn clean install -U -DskipTests -Dmaven.repo.local="$M2" $MAVEN_CLI_OPTS
mvn test jacoco:report -Dmaven.repo.local="$M2" -Dspring.profiles.active=local $MAVEN_CLI_OPTS
mvn checkstyle:check -q -DskipTests -Dcheckstyle.failOnViolation=false $MAVEN_CLI_OPTS
```

4.5 Caso simple: Jenkins para deploy local

En modularstack-app hay un Jenkinsfile minimo para copiar archivos al folder del sitio.

Fuente: /Users/wallfacer/Documents/modularstack-app/Jenkinsfile

```groovy
pipeline {
  agent any
  stages {
    stage('Deploy to local site') {
      steps {
        sh '''
          SITE_DIR="/Users/wallfacer/Sites/modularstack"
          cp -R ./* "${SITE_DIR}/"
        '''
      }
    }
  }
}
```

Ensenanza practica

No todos los pipelines deben ser complejos desde el dia uno.
Puedes comenzar simple y evolucionar por madurez.

5) IMAGEN, CONTENEDOR Y REGISTRY (DETALLE PRACTICO)
====================================================================

5.1 Imagen y contenedor sin complicaciones

Imagen = receta empaquetada.
Contenedor = plato servido ejecutandose.

Si la receta cambia, versionas.
Si el plato falla, puedes volver a receta anterior.

5.2 Caso real de Dockerfile

Fuente: /Users/wallfacer/proyectos-gitlab/pos-online/Dockerfile

```dockerfile
FROM openjdk:11-ea-11-jdk-slim
COPY "./target/pos-online-0.0.1-SNAPSHOT.jar" "pos-online-dev.jar"
ENV TZ="America/Mexico_City"
EXPOSE 3000
ENTRYPOINT [ "java","-Duser.timezone=UTC-7", "-Xmx4096m", "-jar", "pos-online-dev.jar"]
```

Aprendizajes para usuario final

- Existe una base reproducible (FROM).
- Se define como arrancar la app (ENTRYPOINT).
- Se expresa puerto expuesto (EXPOSE).

5.3 Registry como biblioteca operativa

Practica recomendada:
- tag por commit SHA,
- tags de entorno controlados,
- no usar latest como unica referencia en produccion.

5.4 Ejemplo desde ebook: login y push en pipeline

Fuente:
references/book-original/reference-text/_book_reference_txt/chapter2/Jenkinsfile.declarative.txt

```groovy
environment {
    REGISTRY_CREDENTIALS= credentials('DOCKER_REGISTRY')
    REGISTRY_URL = 'https://registry.domain.com'
}

stage('Push'){
    steps{
        sh 'docker login $REGISTRY_URL --username $REGISTRY_CREDENTIALS_USR --password $REGISTRY_CREDENTIALS_PSW'
    }
}
```

Que debe quedar claro

- credenciales seguras,
- autenticacion explicita,
- trazabilidad de publicacion.

5.5 Politica de promotion entre entornos

Dev -> QA -> Preprod -> Prod

Regla:
No saltar etapas sin evidencia de control.

Evidencias recomendadas por promotion:
- pruebas aprobadas,
- resultado de scan,
- registro de aprobacion,
- health checks posteriores.

5.6 Rollback sano

Rollback no es derrota.
Es control.

Condiciones para rollback rapido:
- tags claros,
- manifiestos versionados,
- procedimiento ensayado,
- criterio de activacion definido.

6) KUBERNETES Y HELM (ENTREGA CONFIABLE EN PRODUCCION)
====================================================================

6.1 Que valor agrega Kubernetes

- mantiene estado deseado,
- reemplaza instancias no saludables,
- permite despliegues declarativos,
- facilita escalado.

6.2 Por que Helm importa

Porque separa:
- logica de despliegue (chart),
- configuracion por entorno (values).

Esto reduce duplicidad y errores manuales.

6.3 Ejemplo ebook: deploy con Helm desde Jenkins

Fuente:
references/book-original/reference-text/_book_reference_txt/chapter11/Jenkinsfile.eks.txt

```groovy
stage('Deploy'){
    sh """
        helm upgrade --install watchlist ./watchlist -f values.override.yaml \
            --set metadata.jenkins.buildTag=${env.BUILD_TAG} \
            --set metadata.git.commitId=${getCommitId()}
    """
}
```

Valor para usuario final

- despliegue idempotente,
- metadatos de build y commit,
- mejor trazabilidad para incidentes.

6.4 Ejemplo values.yaml (ebook)

Fuente:
references/book-original/reference-text/_book_reference_txt/chapter11/deployment/helm/watchlist/values.yaml.txt

```yaml
metadata:
  git:
    commitId: none
  jenkins:
    buildTag: none
services:
  registry:
    uri: ''
    secret: ''
deployment:
  tag: ''
```

Lectura practica

- metadata: permite auditoria de "que build deploye".
- services.registry: define origen seguro de imagenes.
- deployment.tag: fija version concreta.

6.5 Estrategias de despliegue recomendadas

Nivel inicial:
- rolling update controlado.

Nivel intermedio:
- blue/green para cambios de mayor riesgo.

Nivel avanzado:
- canary con monitoreo de error budget.

7) TERRAFORM E INFRAESTRUCTURA COMO CODIGO
====================================================================

7.1 Problema que resuelve IaC

Cuando infraestructura se crea a mano:
- se olvida como se hizo,
- se repite con diferencias,
- cuesta auditar,
- cuesta replicar.

IaC resuelve esto dejando configuracion en codigo versionado.

7.2 Snippet base Terraform (ebook)

Fuente: references/book-original/chapters/chapter5/terraform.tf

```hcl
provider "aws" {
  region                  = var.region
  shared_credentials_file = var.shared_credentials_file
  profile                 = var.aws_profile
}
```

Fuente: references/book-original/chapters/chapter5/vpc.tf

```hcl
resource "aws_vpc" "management" {
  cidr_block           = var.cidr_block
  enable_dns_hostnames = true
}
```

Interpretacion simple

- provider define a donde desplegar.
- resource define que recurso crear.
- variables permiten reutilizar por entorno.

7.3 Buenas practicas minimas

- separar modulos por responsabilidad,
- usar remote state seguro,
- revisar plan antes de apply,
- proteger credenciales,
- auditar cambios por pull request.

7.4 Consideracion para servidor propio

Aunque Terraform sea comun en nube, el principio IaC aplica tambien en on-prem:
- red,
- VM,
- balanceadores,
- configuraciones repetibles.

8) SEGURIDAD, CUMPLIMIENTO Y GOBERNANZA
====================================================================

8.1 Seguridad por capas

Capa 1: repositorio
- ramas protegidas,
- revisiones,
- secretos fuera de codigo.

Capa 2: pipeline
- controles de calidad,
- escaneo de dependencias e imagenes,
- firmas o controles de procedencia cuando aplique.

Capa 3: runtime
- minimo privilegio,
- network policies,
- secretos gestionados.

8.2 RBAC en Kubernetes (ejemplo)

Fuente: references/book-original/chapters/chapter11/k8s-dashboard/eks-admin.yaml

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: eks-admin
  namespace: kube-system
---
kind: ClusterRoleBinding
roleRef:
  kind: ClusterRole
  name: cluster-admin
```

Nota operativa

En produccion, usar privilegios minimos para cada rol.
Evitar cluster-admin generalizado para tareas rutinarias.

8.3 Gobernanza pragmatica

Reglas claras y pocas, pero cumplibles:
- definicion de listo para desplegar,
- evidencia obligatoria por release,
- responsables por etapa,
- proceso de incidente y postmortem.

9) OBSERVABILIDAD, CONFIABILIDAD Y OPERACION DIARIA
====================================================================

9.1 Sin observabilidad no hay mejora sostenida

Medir solo si "subio o no subio" no alcanza.

9.2 Minimo viable de observabilidad

- logs centralizados,
- metricas de app y plataforma,
- health endpoints,
- alertas accionables (no ruido).

9.3 Runbook minimo por servicio

Debe incluir:
- como desplegar,
- como validar salud,
- como hacer rollback,
- como escalar incidente,
- quien aprueba que.

9.4 Confiabilidad como habito

Practicas semanales:
- revisar fallos recurrentes,
- validar alertas inutiles,
- actualizar runbooks,
- evaluar tiempo real de recuperacion.

13) KPIS, SCORECARDS Y EVIDENCIA DE PROGRESO
====================================================================

13.1 KPIs principales (DORA)

- Lead Time
Tiempo desde commit hasta produccion.

- Deployment Frequency
Cuantas veces se despliega en periodo.

- Change Failure Rate
Porcentaje de cambios que causan fallo.

- MTTR
Tiempo medio de recuperacion.

13.2 Como medir sin complicarte

Paso 1: define baseline de 4 semanas.
Paso 2: mide semanalmente.
Paso 3: analiza tendencia, no solo valor puntual.
Paso 4: registra acciones de mejora y su impacto.

13.3 Formato de scorecard recomendado

Cabecera:
- semana,
- servicio,
- entorno,
- responsable.

Cuerpo:
- KPI actual,
- KPI anterior,
- variacion,
- comentario de causa,
- accion siguiente.

13.4 Evidencia minima para decisiones ejecutivas

- 1 grafica de tendencia por KPI,
- 3 principales incidentes y aprendizaje,
- 3 mejoras implementadas,
- riesgo abierto y mitigacion.

14) OBJECIONES FRECUENTES Y RESPUESTAS CLARAS
====================================================================

Objecion 1: "No tenemos tiempo para esto"

Respuesta:
No implementar tambien consume tiempo, solo que de forma oculta y reactiva.
Un piloto acotado reduce riesgo y entrega evidencia rapida.

Objecion 2: "Nuestro stack es distinto"

Respuesta:
El principio es agnostico al stack.
Cambia la herramienta puntual, no la logica de control y trazabilidad.

Objecion 3: "No queremos depender de nube costosa"

Respuesta:
El modelo puede operar en servidor Linux propio.
La prioridad es estandar operativo, no proveedor especifico.

Objecion 4: "Automatizar da miedo"

Respuesta:
Automatizar sin controles da miedo.
Automatizar con gates, aprobaciones y observabilidad reduce riesgo.

Objecion 5: "Ya tenemos Jenkins y aun hay problemas"

Respuesta:
Tener herramienta no garantiza sistema.
Lo critico es el diseno del flujo, reglas, ownership y evidencia.

15) MANUAL DE COMUNICACION (CLARO, HUMANO, RESPETUOSO)
====================================================================

15.1 Reglas de estilo

- Claro antes que elegante.
- Especifico antes que ambiguo.
- Evidencia antes que opinion.
- Respeto antes que juicio.

15.2 Frases utiles

En vez de:
"Su proceso esta mal."

Usa:
"Su proceso actual funciono para cierta etapa. Ahora podemos evolucionarlo para escalar con menos friccion."

En vez de:
"Esto es basico."

Usa:
"Este punto es fundamental y vale la pena dejarlo bien claro para todos."

15.3 Preguntas tacticas para abrir conversacion

- Que parte del release genera mas incertidumbre hoy?
- Donde se pierde mas tiempo entre build y produccion?
- Que evidencia usan hoy para decidir rollback?

15.4 Regla de visuales

Una slide, una idea fuerte.
Si una slide no ayuda a decidir, se elimina o se simplifica.
