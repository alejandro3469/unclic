04. PROBLEMA Y RESULTADO DESEADO (NEGOCIO + OPERACION)

Patron enterprise observado

La mayoria de equipos puede construir features.
Menos equipos puede entregarlas en produccion de forma confiable y repetible.

Sintomas frecuentes

- checklists manuales de release,
- drift entre ambientes,
- trazabilidad debil entre commit y runtime,
- rollback lento bajo presion,
- fatiga de equipo por operacion reactiva.

Por que importa para negocio

- baja velocidad de ciclo,
- aprendizaje de producto mas lento,
- mayor riesgo por ventana de release,
- menor confianza interna.

Resultado deseado compartido

- releases mas rapidos y controlados,
- menor impacto por fallas de cambio,
- trazabilidad clara desde commit hasta produccion,
- mayor autonomia con recursos actuales.

06. MODELO DE ADOPCION POR ETAPA

Etapa A: Proceso manual/papel

Meta:
Crear flujo minimo confiable de build-test-package.

Entregables minimos:
- pipeline en repo,
- gates de build/test/lint,
- primer artefacto trazable.


Etapa B: Monolito en crecimiento

Meta:
Estabilizar release antes de escalar arquitectura.

Entregables minimos:
- tags deterministas,
- policy de promotion por entorno,
- procedimiento de rollback.


Etapa C: Evolucion a microservicios

Meta:
Aumentar frecuencia sin aumentar caos.

Entregables minimos:
- pipelines template por servicio,
- estrategia de values por entorno,
- verificacion de rollout y salud.


Etapa D: Cloud own o fully cloud

Meta:
Escalar infra y gobernanza manteniendo velocidad.

Entregables minimos:
- cambios de infra por Terraform,
- politicas de despliegue,
- revisiones operativas por KPIs.

07. JENKINS PIPELINE AS CODE (EVIDENCIA OFICIAL + LIBRO)

Lo que establecen las docs oficiales

- Jenkins permite jobs de pipeline desde Jenkinsfile en repo [DOC-1].
- Declarative Pipeline define agent/stages/steps [DOC-2].
- Jenkinsfile es el archivo canonico para logica de pipeline [DOC-3].

Por que importa en handoff enterprise

- Proceso de release revisable por PR.
- Comportamiento por rama codificado.
- Menor dependencia de conocimiento tacito.

Prueba local

Snippet real de pos-online:

```groovy
stage('Test') {
  steps {
    unstash 'build-output'
    script {
      def test = load '.jenkins/build/test.groovy'
      test.run(this)
    }
    junit allowEmptyResults: true, testResults: 'target/surefire-reports/*.xml'
  }
}
```

```groovy
stage('Deploy') {
  when { anyOf { branch 'main'; expression { env.GIT_BRANCH == 'origin/main' || env.GIT_BRANCH == 'main' } } }
  steps {
    script {
      env.DEPLOY_ENV = params.DEPLOY_ENV ?: 'envPrd'
      input message: "Deploy en servidor (${env.DEPLOY_ENV}). ¿Ejecutar?", ok: 'Sí, ejecutar Deploy'
      def deploy = load '.jenkins/deploy/deploy.groovy'
      deploy.run(this)
    }
  }
}
```

Que demuestra

- Reportes de pruebas como evidencia.
- Compuertas explicitas para pasos sensibles.
- Politica por rama codificada.

08. GOBIERNO DE IMAGENES Y REGISTRY

Base oficial

- Referencia de imagen/tag en Docker [DOC-4].
- Buenas practicas de build [DOC-5].
- Inmutabilidad de tags donde se soporte [DOC-6].

Politica operativa recomendada

- Tag por commit SHA en promociones a prod.
- Evitar depender de tags mutables como unica referencia.
- Relacionar tags con manifiestos y logs de release.

Prueba local

Dockerfile real (pos-online):

```dockerfile
FROM openjdk:11-ea-11-jdk-slim
COPY "./target/pos-online-0.0.1-SNAPSHOT.jar" "pos-online-dev.jar"
ENV TZ="America/Mexico_City"
EXPOSE 3000
ENTRYPOINT [ "java","-Duser.timezone=UTC-7", "-Xmx4096m", "-jar", "pos-online-dev.jar"]
```

Patron de login a registry (book assets):

```groovy
environment {
  REGISTRY_CREDENTIALS = credentials('DOCKER_REGISTRY')
  REGISTRY_URL = 'https://registry.domain.com'
}
stage('Push') {
  steps {
    sh 'docker login $REGISTRY_URL --username $REGISTRY_CREDENTIALS_USR --password $REGISTRY_CREDENTIALS_PSW'
  }
}
```

09. CONTROL DE DESPLIEGUES CON KUBERNETES Y HELM

Base oficial

- Deployments como controlador declarativo [DOC-7].
- Rollout status verificable por kubectl [DOC-9].
- Probes para salud y readiness [DOC-8].
- Helm upgrade con values y overrides [DOC-10].

Implicaciones practicas

- Definir desired state y no depender de pasos manuales opacos.
- Exigir health checks reales para declarar exito de deploy.
- Gestionar configuracion por entorno con values.

Prueba del libro

Despliegue con Helm desde Jenkins:

```groovy
stage('Deploy') {
  sh """
    helm upgrade --install watchlist ./watchlist -f values.override.yaml \
      --set metadata.jenkins.buildTag=${env.BUILD_TAG} \
      --set metadata.git.commitId=${getCommitId()}
  """
}
```

Values con metadata y tag:

```yaml
metadata:
  git:
    commitId: none
  jenkins:
    buildTag: none
services:
  registry:
    uri: ''
    secret: ''
deployment:
  tag: ''
```

11. SEGURIDAD, CONFIABILIDAD Y PREPARACION OPERATIVA

Principios de seguridad

- Credenciales fuera del codigo fuente.
- Trazabilidad de release con metadata.
- Accesos por minimo privilegio en runtime.

Principios de confiabilidad

- Probes como criterio tecnico de salud [DOC-8].
- Rollout status verificable [DOC-9].
- Rollback definido por tags conocidos.

Principios de preparacion operativa

- Runbook por servicio: deploy, validar, rollback, escalar.
- Verificacion post-deploy estandar.
- Revision semanal de KPIs.

Prueba local del libro (RBAC ejemplo):

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: eks-admin
  namespace: kube-system
---
kind: ClusterRoleBinding
roleRef:
  kind: ClusterRole
  name: cluster-admin
```

Nota:
En produccion, adaptar a minimo privilegio; evitar privilegios amplios por defecto.

15. MODELO DE KPIS Y SCORECARDS

KPIs primarios

- Lead Time
- Deployment Frequency
- Change Failure Rate
- MTTR

Regla de medicion

- baseline de 4 semanas,
- seguimiento semanal,
- accion correctiva por variacion.

Regla de decision

Escalar solo cuando:
- tendencia KPI mejora,
- eventos de confiabilidad bajan,
- ownership post-handoff es estable.

16. OBJECIONES Y RESPUESTAS BASADAS EN EVIDENCIA

Objecion: No hay presupuesto ahora.

Respuesta:
Se arranca con piloto acotado.
El costo de no actuar es valor retrasado + desgaste + incidentes evitables.

Objecion: Nuestro stack es distinto.

Respuesta:
La arquitectura de flujo es agnostica al stack.
Se adapta implementacion, no el principio.

Objecion: Operamos en Linux propio.

Respuesta:
Este modelo soporta infraestructura propia.
No exige migracion inmediata a cloud.

Objecion: Automatizar sube riesgo.

Respuesta:
Automatizar sin control sube riesgo.
Automatizar con gates y observabilidad reduce riesgo.

17. SCRIPT DE CIERRE PARA CONVERSION CON INTEGRIDAD

Cierre sugerido

No les pedimos fe.
Les proponemos mecanismo con evidencia.

Nos adaptamos a su etapa actual:
manual, monolito, microservicios o cloud.

Nuestro compromiso es operativo:
- entregar codigo,
- entregar proceso,
- entregar transferencia,
- acompañar al equipo en ejecucion real.

- servicio piloto,
- baseline KPI,
- responsables,
