04. PROBLEM AND DESIRED OUTCOME (BUSINESS + OPERATIONS)

Observed enterprise pattern

Most teams can build software.
Fewer teams can reliably ship value to production at a repeatable cadence.

Common symptoms

- Manual release checklists with inconsistent execution.
- Environment drift between build/test/prod.
- Unclear artifact-to-release traceability.
- Slow rollback under incident pressure.
- Team fatigue caused by reactive operations.

Why this matters beyond engineering

- Business cycle time slows.
- Product learning loops are delayed.
- Risk accumulates in each release window.
- Team energy drops due to repetitive fire-fighting.

Desired outcome (shared by technical and business stakeholders)

- Faster controlled releases.
- Lower change failure impact.
- Clear audit trail from commit to runtime.
- Higher operational autonomy with current resources.

07. JENKINS PIPELINE AS CODE (OFFICIAL + BOOK EVIDENCE)

What official docs establish

- Jenkins can manage pipeline jobs from repository code via Jenkinsfile [DOC-1].
- Declarative Pipeline syntax defines agent/stages/steps patterns [DOC-2].
- Jenkinsfile is the canonical file for pipeline logic in source control [DOC-3].

Why this matters for enterprise handoff

- Release logic is reviewable via pull request.
- Branch-aware behavior supports environment policy.
- Changes in process can be versioned alongside application code.

Local-book and local-repo proof

Snippet pattern from local production pipeline (pos-online):

```groovy
stage('Test') {
  steps {
    unstash 'build-output'
    script {
      def test = load '.jenkins/build/test.groovy'
      test.run(this)
    }
    junit allowEmptyResults: true, testResults: 'target/surefire-reports/*.xml'
  }
}
```

```groovy
stage('Deploy') {
  when { anyOf { branch 'main'; expression { env.GIT_BRANCH == 'origin/main' || env.GIT_BRANCH == 'main' } } }
  steps {
    script {
      env.DEPLOY_ENV = params.DEPLOY_ENV ?: 'envPrd'
      input message: "Deploy en servidor (${env.DEPLOY_ENV}). ¿Ejecutar?", ok: 'Sí, ejecutar Deploy'
      def deploy = load '.jenkins/deploy/deploy.groovy'
      deploy.run(this)
    }
  }
}
```

What this proves

- Test reports are codified in pipeline.
- Production-sensitive steps use explicit approvals.
- Branch policy is encoded, not tribal knowledge.

08. CONTAINER IMAGE AND REGISTRY GOVERNANCE

Official baseline

- Image references include host/namespace/repository/tag structure [DOC-4].
- Tag defaults and naming implications affect traceability [DOC-4].
- Docker build best practices emphasize small base images and regular rebuilds [DOC-5].
- Immutable tags (where supported) reduce overwrite risk [DOC-6].

Operational policy derived from docs + field practice

- Use commit SHA tags for hard traceability.
- Avoid relying on mutable tags alone for production promotion.
- Keep release tags tied to deploy manifests and audit logs.

Local proof

Dockerfile example from local production app:

```dockerfile
FROM openjdk:11-ea-11-jdk-slim
COPY "./target/pos-online-0.0.1-SNAPSHOT.jar" "pos-online-dev.jar"
ENV TZ="America/Mexico_City"
EXPOSE 3000
ENTRYPOINT [ "java","-Duser.timezone=UTC-7", "-Xmx4096m", "-jar", "pos-online-dev.jar"]
```

Jenkins declarative registry login pattern from local book assets:

```groovy
environment {
  REGISTRY_CREDENTIALS = credentials('DOCKER_REGISTRY')
  REGISTRY_URL = 'https://registry.domain.com'
}
stage('Push') {
  steps {
    sh 'docker login $REGISTRY_URL --username $REGISTRY_CREDENTIALS_USR --password $REGISTRY_CREDENTIALS_PSW'
  }
}
```

09. KUBERNETES AND HELM DEPLOYMENT CONTROL

Official baseline

- Deployments provide declarative updates and controlled rollout behavior [DOC-7].
- Rollout status can be watched/pinned in kubectl [DOC-9].
- Liveness/readiness/startup probes define health and traffic readiness semantics [DOC-8].
- Helm upgrade supports layered values and explicit overrides [DOC-10].

Operational implications

- Use deployment manifests to control desired state transitions.
- Use readiness/liveness/startup probes to reduce false-success rollouts.
- Use helm values files for environment-specific behavior.

Local-book proof

Helm upgrade from Jenkins (book chapter11):

```groovy
stage('Deploy') {
  sh """
    helm upgrade --install watchlist ./watchlist -f values.override.yaml \
      --set metadata.jenkins.buildTag=${env.BUILD_TAG} \
      --set metadata.git.commitId=${getCommitId()}
  """
}
```

Values structure with metadata and deployment tag:

```yaml
metadata:
  git:
    commitId: none
  jenkins:
    buildTag: none
services:
  registry:
    uri: ''
    secret: ''
deployment:
  tag: ''
```

11. SECURITY, RELIABILITY, AND OPERATIONAL READINESS

Security principles used

- Credentials managed through pipeline credential systems, not hardcoded secrets.
- Release traceability through build metadata and tagged artifacts.
- Access control and least privilege in cluster operations.

Reliability principles used

- Health probes drive traffic and restart behavior [DOC-8].
- Rollout status monitored explicitly [DOC-9].
- Rollback path tied to known image tags.

Operational readiness principles used

- Runbook per service (deploy, verify, rollback, escalation).
- Observable post-deploy checks (health + rollout status).
- Weekly KPI review to prevent silent degradation.

Local-book proof for cluster access object:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: eks-admin
  namespace: kube-system
---
kind: ClusterRoleBinding
roleRef:
  kind: ClusterRole
  name: cluster-admin
```

Note:
Use least-privilege adaptations for production governance; avoid broad admin bindings unless strictly needed.
